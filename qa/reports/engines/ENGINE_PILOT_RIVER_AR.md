# تجربة المحرك الأولى — عبور النهر على PixiJS 8

## البنية
- `ui/engines/scene-kit.js`: يربط منطق اللغز بمحرك الرسم. يقرأ `ui/engines/scenes/<id>.json`، ويحمّل **المحرك الذي يحتاجه اللغز فقط** (PixiJS أو Konva) عند أول فتح، ثم ملف العرض `ui/engines/renderers/<id>.<engine>.js`.
- المنطق والقواعد والحفظ لم تتغير. لوح النهر يرسل للعرض ما تغيّر فقط: `view.update({side, sailing, passengers})`.
- كل الإحداثيات (حجم اللوحة، المرسيان، طبقات القارب، المقاسات، التوقيتات) والملفات في `scenes/pz_river.json`. استبدال الفن = تعديل هذا الملف ومجلد الفن.
- إن فشل تحميل المحرك أو الفن يبقى لوح DOM الحالي ويُلعب عاديًا (مختبر بحجب PixiJS).
- لا حلقة إطارات في الخمول: الرسم فقط أثناء حركة القارب (أوقفت مؤقّت Pixi الداخلي الذي كان يستهلك ~15 ms/ث).
- الفن الحالي مؤقت (Gemini)، موصول فقط لتشغيل المحرك. لم أرسم شيئًا جديدًا.

## القياس (Chromium، 390×844، خادم يحاكي GitHub Pages)
| | DOM (main) | PixiJS (الفرع) |
|---|---|---|
| أول فتح — حتى ظهور مشهد Pixi | 246 ms | 735 ms |
| فتح ثانٍ | 108 ms | 277 ms |
| بيانات أول فتح | 910 KB | 1165 KB (+256 KB مكتبة PixiJS مضغوطة) |
| شبكة بطيئة + معالج ×4، أول فتح | 0.7 ث | 8.0 ث حتى مشهد Pixi |
| ذاكرة JS | 6.9 MB | 9.2 MB |
| عمل المعالج في الخمول | 1.3 ms/ث | 1.2 ms/ث |

اللوح قابل للعب فورًا في الحالتين: يظهر DOM أولًا، ثم يحل مشهد Pixi محله بنفس المواضع.

**الخلاصة الصريحة:** مع الفن الحالي PixiJS أثقل ولا يضيف شيئًا مرئيًا. قيمته تظهر مع فن Work المتحرك (طبقات، رذاذ، ماء، شخصيات). أنصح بتحميل PixiJS مسبقًا في وقت الخمول بعد فتح «مكتبة الألغاز» حين تصل تصاميم Work، لإخفاء تكلفة أول فتح.

## الاختبارات
- `qa/browser/river_pixi.py`: Chromium وWebKit 44/44 — المشهد يعمل، قارب DOM فوق قارب Pixi، الحل الأمثل يفوز، زر العبور الكبير تحت القارب، لا أخطاء، اللوح يُنظَّف عند الإغلاق، وعند حجب المحرك يبقى DOM ويُلعب.
